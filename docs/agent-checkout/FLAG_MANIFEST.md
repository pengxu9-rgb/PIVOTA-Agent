# Protocol-door flag manifest

**Authoritative per-environment snapshot of every env flag that gates a
protocol door or a money path**, across PIVOTA-Agent (the gateway — all public
doors, ADR-021) and pivota-backend (money execution). Production readiness is a
config question: the doors are code-complete and env-gated, so *this page* is
what "what is live?" means.

**Snapshot date: 2026-08-11** (read from Railway service env, not from
defaults). Update this table in the same PR as any flag flip — a stale manifest
is worse than none.

> Environment-detection caveat: **prod sets `RAILWAY_ENVIRONMENT=production`
> but NOT `NODE_ENV`** (either service). Any `NODE_ENV`-only production guard
> is inert in prod; guards must check `RAILWAY_ENVIRONMENT`/`VERCEL_ENV` too
> (pattern: `isProductionLikeAuroraBffEnv`).

| `AGENT_CHECKOUT_STORE_CART_IDEMPOTENCY_ENABLED` | absent (off) | Both checkout doors' storefront path: a retried create returns the same checkout | OFF. Read per call. Accepted on-values: `1`, `true`, `yes`, `on` (any case). On: same PARTNER + same verified buyer + same session (`acp_session_id`) + same door + same idempotency key + same request (lines, chosen variants, market named or assumed, discount codes, seller named, expected seller) within 6 h (the `esc_` id's own `expires_at`) → the SAME `esc_` id, read back with `get_cart`: no second `create_cart`, referral or hand-off record. Same key, different request → `IDEMPOTENCY_CONFLICT` (terminal, the kernel ledger's code and meaning). Two at once: one builds (30 s claim), the other waits up to 12 s and reads the same checkout, else `CHECKOUT_OUTCOME_UNKNOWN` (retriable with the same key). The two doors do not share keys. UNDER THE CURRENCY RULE (`AGENT_CHECKOUT_UCP_CURRENCY_FOLLOWS_MARKET`; on `/mcp` this path runs only with it) A RETRY IS JUDGED AGAIN, NEVER SERVED FROM ITS RECORD: the recorded checkout is read back through the same judgement as any re-read, so a record made before the rule was on (or for rows no longer in the market's currency) is refused by name (`seller_not_priced_in_market_currency`, the same refusal a fresh create of that request gets) with no seller asked; a market with no currency is refused `market_not_priced` BEFORE the ledger is consulted (no claim, no count); a create the rule refuses writes no record. WHAT `replayed` COUNTS: `replayed` / `replayed_after_wait` (counter and log `outcome`) mean a record was FOUND and read back, not that a checkout was served; a read-back that hands out nothing (refused by the currency rule, the gate or a changed row) is counted and logged once more as `replay_refused` with the refusal's `reason` (`declined` when the gate declined). Served replays = `replayed` + `replayed_after_wait` - `replay_refused`. THE PARTNER is the caller the gateway verified (the agent of an api-key call; the issuer and client of an OAuth call; the same subject the partner assertion is signed for): one person using two partners' agents gets two checkouts, each with its own referral, and a key reused in another session builds a new checkout, as on the kernel path. "Session" is the call's `acp_session_id`: on the OAuth door, when the access token carries no session claim, that is the `Mcp-Session-Id` header the CLIENT sends (the gateway neither issues nor checks it), so a client that reconnects under a new session id is NOT deduplicated: its retry builds a second cart, as with the flag off. Only the partner and the buyer are verified on every door; after the flip compare `claimed` with `replayed` per door to see how much an OAuth client's retries are deduplicated (subtract `replay_refused`: `replayed` includes read-backs that were refused). A call bound to no partner (a service or degraded identity) or to no session is NOT deduplicated: it builds as with the flag off, logged `outcome: fail_open` `stage: no_partner` / `no_session`. While the flag is on, a key shorter than 8 characters (the `minLength` both tool schemas publish) is refused on the storefront path before the gate or any store call: `IDEMPOTENCY_CONFLICT`, the code a missing key gets, `detail.reason: idempotency_key_too_short`, logged `outcome: key_too_short` (the length is counted after removing surrounding blanks and in UTF-16 code units, which is not exactly the schema's count: eight characters padded with blanks are refused, four astral characters are accepted; the shared intake rule is to replace this one); the kernel path does not enforce the minimum. Records live in the kernel's state store (`commerce_kv`, namespace `storefront_cart_idempotency`; Postgres wherever strict checkout runs): a digest key, the request digest and the id sealed to (door, partner, buyer, session, key), the record key, the seal and the stored request digest all under a key derived from `CONFIRMATION_SECRET` (the id binding's secret and derivation, a label of its own; no new secret), so a row cannot be found or opened from values a caller knows; no link, total, email or id in clear. Store missing or failing, or `CONFIRMATION_SECRET` unset or under 16 characters (`stage: no_secret`; no record is written) → FAIL OPEN to today's behaviour, logged `storefront_cart_idempotency` `outcome: fail_open`. Rotating `CONFIRMATION_SECRET` orphans the outstanding records (6 h life): a retry after a rotation builds a new cart. **Before on:** the gateway's `commerce_kv` table reachable (it is for strict checkout); `CONFIRMATION_SECRET` identical on every instance (a record written by one instance is read by the others only under the same secret) and not about to rotate; partners told that a reused key with another cart in the same session is now refused on the storefront path, and that a key under 8 characters is refused there; no partner's storefront creates send keys under 8 characters today (count them first: every one becomes a refusal); watch `fail_open` (by `stage`: a steady `no_partner` means a partner's calls are arriving under a service or degraded identity and are not being deduplicated), `key_too_short`, `in_flight` and `replay_refused` counts after the flip (never read `replayed` alone as "served"). A replayed seller-priced answer carries no per-code discount messages (only what the seller's cart holds). Rollback: unset (records expire on their own). |
| `AGENT_CHECKOUT_STORE_CART_ID_BINDING` | absent (off) | Both checkout doors: a storefront checkout id (`esc_`) is bound to the buyer that created it | A MODE, read per call: `off` (default; ANY other value, `1`/`true`/`on` included, is off), `mint`, `enforce`. `mint`: every new id is `v: 3` with `b`, an HMAC over the id's members and the creating buyer's verified `user_ref`, under a key derived from `CONFIRMATION_SECRET` (no new secret); unbound (v1/v2) ids are still read. `enforce`: as mint, and an unbound id is no id of ours.
