# Canonical history in the discovery feed

A recent view of a canonical `sig_…` product now resolves that exact public stored subject before selecting a personalized canonical reader. The reader obtains brand and taxonomy from the stored catalog, checks the observed merchant and conflicting history brand/domain, and reads public live canonical candidates directly. It does not infer beauty from a brand name or round-trip through the backend SDK search proxy.

The new reader applies to home and browse history on the existing canonical-index profile, with US/en-US serving and no explicit query, category, brand scope or separate source-product scope. Explicit scopes, other locales/markets and noncanonical history retain their established initial route. A different history query is not silently replaced by the stored brand. Canonical candidates retain only in-stock US/USD own offers and their corresponding price; nonpublic, expired and suppressed sources are excluded. This is catalog-read behavior and does not expand checkout eligibility or buyer permissions.

Once this primary reader is selected, errors remain provider failures and a clean empty result stays empty. It never retries another catalog provider or the relationship graph after an empty/error result. The provider/source metadata names `canonical_sig_personalized`; the runtime smoke contract accepts that declared source while retaining all product-count, history suppression and degradation checks.

The canonical view stores `category_path` as text. Both text and array inputs are now mapped to the same path without inventing a category. Parallel discovery search steps with exactly identical request URL, params, headers, context and deadline are coalesced within a single request. The secondary logical label is reported as coalesced/skipped with zero returned products and zero transport latency, and does not count as another circuit-breaker result. Distinct queries/offsets/limits remain separate.

No checkout selection, money binding, owner/session recovery, alternate checkout executor, provider configuration or timeout budget is changed. Production completion still requires an independent source review, green CI, exact serving-image provenance, and successful primary runtime checks using the original public Iconic Starter Ritual history on both home and browse surfaces. Local mocked and PostgreSQL tests demonstrate source semantics, not production latency acceptance.

Canonical history browse excludes the original recent views from the entire paging universe on every page and never fills an underfull page with those suppressed items. Signature ordering makes equal refresh times deterministic. Legacy initial routes retain their existing paging behavior.

Canonical personalized browse uses one page-independent, at-most-400-row stored public universe (the existing canonical reader maximum) before sorting and suppression. Page/limit/cursor changes cannot expand this universe. Viewed subjects stay excluded from both every page and its bounded total; the reported count source is `runtime_canonical_history_pool`. It does not launch the unrelated global catalog count. If stored history instead leaves the existing initial query route selected, that route keeps its original count behavior. Static-universe paging is tested with real PostgreSQL and a cheaper/more expensive item beyond the previous 30/36-row boundary; this does not promise stable offsets when the underlying catalog changes between requests.

## Cold exact-brand queries

A browse query with no recent views/queries, explicit brand/category scope or source product may choose the stored canonical reader before any transport request. This applies only to the existing canonical feature profile, US offers and en-US locale. The query must equal the brand on a live, unsuppressed catalog product with its own public trust row and the same canonical view brand; case and outer spaces are ignored, but aliases, substrings and additional query terms cannot grant admission.

A known brand uses the same bounded 400-candidate universe, strict own-listing US/USD in-stock offers, existing relevance/domain/money filters and stable signature ordering. Its total is the filtered runtime pool count. Unknown brands and free text retain their intentionally selected initial query route. Other explicit scopes and history retain their existing routes.

Malformed or failed admission is an honest primary error. Once a known brand is selected, empty offers or a failed canonical pool remain empty/error: no SDK search, graph recall or alternate provider is dispatched. Budgets are unchanged; no retry or cache warming is required to select this route.

The PostgreSQL CI job executes `discovery_canonical_brand_query_postgres.test.js`, including a first published `/agent/shop/v1/invoke` query over real admission/pool SQL. Its catalog rows are synthetic, authentication uses the local test bypass, and ancillary hydration/count projections are stubbed empty; it proves route/projection behavior rather than production latency.


## Shared public source and official listing admission

The canonical generic cold reader, canonical history anchors/pool, and newly selected exact-brand query pool now share public, live, unsuppressed source selection and eligible own-product offers. Cards use the current admitted offer amount rather than the materialized view's cached amount or aggregated foreign offers. The non-strict explicit brand-page reader (`strictPublicSource=false`) keeps its existing projection; this change does not claim that every brand-page/catalog reader uses the new policy.

A native enrichment official listing can retain an `agent_seed::` offer seller while apply adopts an observed CP/SKU seller of record. The new supported arm requires the same product and own SKU, native enrichment provenance on CP/offer/active indexable merchant registry, official brand-direct/first-party policy, exact HTTPS source/destination/canonical listing agreement, and registry source/domain agreement. The offer seller must be exactly the native normalized namespace derived from the selected CP brand. This deliberately supports the official same-brand listing subset; different validated retailer names, query/fragment URLs, ambiguous source identity, or disagreement remain excluded. The established same-merchant arm is unchanged.

The production diagnostic captured the original public Iconic CP/SKU and active official offer/registry listing scalars, but did not capture `own_cp.brand` or payload/version/name scalars. The namespace condition is justified by the native producer contract and isolated producer/apply tests, not by inventing additional production evidence. Original deployed cold→Iconic history→browse and price/identity checks remain required after release. Source labels alone, cached view money, or an arbitrary same-product merchant do not grant admission.

An exact public history subject with no eligible own offer is a healthy empty eligibility outcome, `canonical_history_item_unavailable`, exposed in provider breakdown and debug recall metadata. Missing/private subjects and real database failures retain their failure classifications. Once history or exact-brand canonical primary is selected, this outcome never dispatches another provider. Generic cold's established coverage policy is unchanged.

Regression tests use real PostgreSQL source/offer/registry/SKU rows and published HTTP discovery routes for cold→original history→browse, current49 versus cached45, and strict foreign/private/suppression/market/currency/stock/URL/SKU negatives. Ancillary identity/hydration/count projections and test authentication remain explicitly synthetic. A separate rollback test runs the native producer and selected apply stages through the actual reader SQL. Neither test establishes live checkout clearance or provider acceptance.

## Storefront-recorded history and fail-soft personalization (2026-10-04)

The storefront (pivota-agent-ui) records a view from the public PDP as `{product_id: sig_…, merchant_id: <PDP product.merchant_id>}`, which for a mirrored product is the observed listing merchant (`merch_obs_…`), not the canonical card's shared external-seed merchant convention. Comparing the view to the card's `merchant_id` refused every storefront-recorded mirror view as `canonical_history_subject_conflict`. The anchor read now also returns `public_listing_merchant_ids`: every merchant with a public, live, unsuppressed listing of the same canonical product. A view is accepted when its merchant is the card merchant, one of those listing merchants, or an own offer seller. A merchant with no public listing of the sig is still refused.

`agent_pdp_view.category_path` is usually a bare leaf (`Serum`, `Beauty Product`, `gift-set`) or NULL, while the profile's `dominantDomain` uses the `DOMAIN_KEYWORDS` vocabulary (`beauty`, `apparel`, …). The stored path is now mapped into that vocabulary from the stored labels only (a taxonomy root as-is, a leaf via the shared label classifier, an unclassifiable single leaf as unknown). Brand and caller text never widen the stored brand or domain; an unknown stored domain under an explicit history domain is still a conflict.

Personalization fails soft. When the history subject does not resolve (subject/domain/currency conflict, not public, ambiguous, unavailable, query error), its own listing is unavailable (`canonical_history_item_unavailable`), or its stored scope holds nothing beyond the suppressed views (`canonical_history_pool_empty`), the request is served the canonical_sig cold feed and ranked as the same request without history (`cold_start_curated`). This supersedes "a clean empty result stays empty" above for those cases. No legacy SDK, seed ladder or relationship graph is dispatched. The reason is recorded as `fallback_reason`, `history_fallback_reason`, the canonical_sig provider breakdown `history_failure_reason`/`history_fallback`, and an unresolved history recall step labelled `canonical_sig_personalized_unresolved`. If the cold read also fails, the catalog failure is still raised. Viewed canonical sigs are suppressed by id on both paths.

The release-gate smoke accepts that declared cold fallback only for the stored-data outcomes (`canonical_history_pool_empty`, `canonical_history_item_unavailable`, `canonical_history_domain_conflict`) and still fails when the feed's own card does not resolve as a subject.
