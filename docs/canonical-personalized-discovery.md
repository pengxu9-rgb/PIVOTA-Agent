# Canonical history in the home feed

A recent view of a canonical `sig_…` product now resolves that exact public stored subject before selecting a personalized canonical reader. The reader obtains brand and taxonomy from the stored catalog, checks the observed merchant and conflicting history brand/domain, and reads public live canonical candidates directly. It does not infer beauty from a brand name or round-trip through the backend SDK search proxy.

The new reader applies to home history on the existing canonical-index profile, with US/en-US serving and no explicit query, category, brand scope or separate source-product scope. Explicit scopes, other locales/markets and noncanonical history retain their established initial route. A different history query is not silently replaced by the stored brand. Canonical candidates retain only in-stock US/USD own offers and their corresponding price; nonpublic, expired and suppressed sources are excluded. This is catalog-read behavior and does not expand checkout eligibility or buyer permissions.

Once this primary reader is selected, errors remain provider failures and a clean empty result stays empty. It never retries another catalog provider or the relationship graph after an empty/error result. The provider/source metadata names `canonical_sig_personalized`; the runtime smoke contract accepts that declared source while retaining all product-count, history suppression and degradation checks.

The canonical view stores `category_path` as text. Both text and array inputs are now mapped to the same path without inventing a category. Parallel discovery search steps with exactly identical request URL, params, headers, context and deadline are coalesced within a single request. The secondary logical label is reported as coalesced/skipped with zero returned products and zero transport latency, and does not count as another circuit-breaker result. Distinct queries/offsets/limits remain separate.

No checkout selection, money binding, owner/session recovery, alternate checkout executor, provider configuration or timeout budget is changed. Production completion still requires an independent source review, green CI, exact serving-image provenance, and successful primary runtime checks using the original public Iconic Starter Ritual history. Local mocked and PostgreSQL tests demonstrate source semantics, not production latency acceptance.
