# Private backend service authentication

The gateway can call a private Cloud Run backend without replacing application credentials. Set both `GATEWAY_BACKEND_ID_TOKEN_AUDIENCE` and `GATEWAY_BACKEND_ID_TOKEN_TARGET_ORIGIN` explicitly. Unset both retains the existing transport. A partial or invalid configuration refuses server construction.

The audience must be the stable HTTPS `*.run.app` receiving-service origin, without a tag, path, port, credentials, query or fragment. The target must be that origin or an explicitly configured traffic-tag origin belonging to the same stable service. `PIVOTA_API_BASE` and `AGENT_AUTH_INTROSPECT_URL` must point to that exact target origin. A custom domain is not accepted as an audience. Request/merchant input never selects an audience.

`src/services/privateBackendHop.js` reuses the bounded refreshing metadata-token provider. It obtains tokens only from the fixed Cloud Run metadata endpoint, shares concurrent acquisition, refreshes before expiry, sanity-checks audience/expiry and adds `X-Serverless-Authorization: Bearer <ID token>`. Cloud Run performs signature verification. The application agent `Authorization`, `X-API-Key`, signed buyer `X-Agent-User-JWT` and introspection `X-Internal-Key` remain intact. Redirects are disabled.

Actual server wiring covers the Reap create/read/recover fetch transport, the federated identity registry fetch, and Axios requests to the exact backend origin (including API-key and checkout-token introspection and ordinary catalog proxy calls). Unrelated merchant Axios requests receive no platform token. This does not arm merchant sourcing or Reap creates. Separate rehearsal target/egress/startup guards remain required.

Missing, expired, wrong-audience or unavailable metadata tokens never fall back to application-only transport. Private HTTP401/403 is unavailable for Reap create/read/recover, preserving checkout uncertainty rather than offering another purchase. API-key introspection maps private IAM failures to `AUTH_INTROSPECT_IAM_FAILED`, excluding stale-verdict and emergency auth replay. A private IAM failure fetching federated issuer bindings cannot reuse stale registry trust.

For isolated staging, the receiving service needs an explicitly reviewed invoker binding for the dedicated gateway service account. Pin application secrets (database DSN, internal introspection key and any required service key) to actual numeric Secret Manager versions in the deployment manifest; `latest` and inherited shared staging bindings are not acceptance evidence. The platform ID token is short-lived metadata output, not a stored secret. Do not print token/secret values. UI390 remains loopback-only: an owned separately reviewed IAM proxy must preserve its original headers and buyer session; this change does not claim a deployed HTTPS UI.

Reference: [Cloud Run service-to-service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service) documents the stable audience for traffic-tag URLs and `X-Serverless-Authorization` for applications that already use `Authorization`.
