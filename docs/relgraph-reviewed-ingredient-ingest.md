# Exact reviewed ingredient evidence

`relationshipReviewedIngredientEvidence.js` provides a separate append-only lane for at most 17 exact listings per transaction. It does not run extraction, models, migration, or ingestion automatically. Legacy ingredient behavior remains unchanged when migration 062 has not been applied. Existing conflict, variant, dupe, offer, and approval thresholds remain in place.

## Source and review contract

Pass records with schema `relgraph.reviewed_ingredient_evidence.v1`, a complete frozen `identity` (product key/signature/external ID, merchant, platform, market, variant title and detail), the complete `ingredient_text`, `formula_sha256` of its trimmed UTF-8 text, `raw_source_sha256` of actual response bytes, and `source_observed_at` from completion of the actual exact PDP fetch. Import, storage, extraction-generation and review timestamps never establish source freshness. Acquisition must stop on redirects, challenge pages, identity/market/variant mismatch or insufficient full formula.

Every input includes the actual `raw_source_body` Buffer, bounded to 2 MiB. The writer checks its fingerprint and its text support for the retained `source_capture.source_excerpt`, bounded to 8,000 characters. HTML tags and script/style bodies are removed; common and numeric entities, Unicode normalization, case and punctuation are normalized consistently for grounding. Ingredient order is preserved. This bounded normalization is deliberately conservative; unsupported encodings or absent DOM text require acquisition/review repair. Raw response bytes are checked in memory and never persisted in the evidence row or receipt.

`source_capture` requires `capture_method: bound_pdp_fetch`, an actual `capture_id`, the same identity, URL, source time and fingerprints, `source_excerpt`/`source_excerpt_sha256`, and explicit `exact_listing_verified` and `full_ingredient_list` results. Complete-list status must come from the real review; five entries alone does not establish completeness.

The stored status gate requires `parse_status: OK`, `review_status: APPROVED`, `audit_status: PASS`, `ingest_allowed: true`. No defaults confer these results. `reviews` contains either independent GPT and Gemini approvals, or one actual human approval after escalation. Each binds the same immutable identity, market, URL, source observation time, raw source hash, formula hash and excerpt hash; supplies its real `review_id`, `reviewed_at`, exact full-formula `grounded_quote`, and explicit full-list, exact-listing and source-grounded results. Disagreement, rejection, partial quotes, review before capture, future or over-45-day source observations fail validation.

Reviews may additionally retain a bounded primitive `model` identifier and a strict SHA-256 `packet_sha256`. The reviewed production operator must provide its actual pinned provider/model and frozen-packet linkage. These fields remain optional for historical synthetic fixtures; their absence does not authenticate an actual provider call. The validator checks supplied proof and never invokes or independently authenticates model providers. Arbitrary response payloads, raw bytes and credentials are forbidden in persisted capture/review metadata.

Neither `supersedes` nor `reconciliation` is supported in this initial lane. Existing formula disagreement, explicit rejection/ingest denial or an incomplete existing evidence scan stops the entire transaction. Conflicted trusted human evidence is never silently replaced. A new exact fact cannot erase a legacy conflicting row from graph hydration.

## Operator sequence

1. Recover the exact listing cohort in memory, capped at 17. Bind the current authoritative PDP URL independently of the extractor. Capture exact PDP response bytes and response-completion time through the approved egress; retain source bytes privately in process.
2. Obtain real independent GPT/Gemini reviews of the frozen complete formula and exact captured source, escalating disagreements to a human. Construct the record only from those completed results. No ingredient record may be published from extractor metadata alone.
3. Verify migration 062 against the **same main database used by the relationship-graph query function**. The graph's targeted `pci_kb.sku_ingredients` query currently uses that connection, rather than the separate `PCI_KB_DATABASE_URL` client; placing the new table in a different KB database does not make it visible.
4. Apply migration 062 only through the reviewed schema deployment process. Attest table columns, check constraints, the identity/product/signature indexes, and both UPDATE/DELETE and TRUNCATE denial triggers. No source runtime path applies DDL. Run a rollback-only transaction proving insert, rejected-status constraint and mutation/truncate refusal before publication.
5. Call `appendReviewedIngredientEvidence({pool, records, nowMs, apply:false, rebindExactListing})`. A mandatory independently reviewed `rebindExactListing({client,record})` callback must hydrate the exact current catalog/seed listing and its authoritative source refs using **that same transaction client**, returning the current product snapshot. Do not return an earlier in-memory/exported manifest or query a separate pool. The writer checks the full identity fingerprint and authoritative current URL again, before inspecting or appending evidence. This acquires one SERIALIZABLE transaction/client, binds advisory locks to sorted exact identities, and reads existing new/beauty/pci ingredient rows without serving filters, including denied evidence. Per-store scans use a 5-row sentinel and refuse more than four matches. The dry run rolls back and writes zero records.
6. After independent source/operator review and green CI, call the same function with the same immutable record inputs and `apply:true`. It reruns transactional checks and appends at most 17 records; a duplicate identical proof is idempotent via `ON CONFLICT(evidence_id) DO NOTHING`. Errors before a commit attempt roll back the transaction. If the COMMIT response is lost, the function returns `status: publication_outcome_unknown`, `kb_writes: null`, durable `evidence_ids`, and `retry_allowed: false`, discarding the uncertain client. Do not claim rollback or blindly retry: reconcile those exact IDs and fingerprints in a later read-only transaction to establish durable outcome first. Normal receipts expose counts only; uncertain receipts additionally expose proof hashes. Do not log raw records, source bytes, identities, URLs, DSNs or model responses.
7. Hydrate the same cohort again and perform the bounded quality measurement. Exact identity scope must match the new lane both before per-target ranking and during later candidate evidence merge. The optional load uses the existing global cap and four-rows-plus-sentinel per-target bounds. Readiness derives its clock only from `source_observed_at`; approved evidence can still become stale, incomplete or conflicting.

Example invocation inside a reviewed in-memory operator (no credential arguments):

```js
const { appendReviewedIngredientEvidence } = require('./src/services/relationshipReviewedIngredientEvidence');
const receipt = await appendReviewedIngredientEvidence({ pool: exactGraphDatabasePool, records: reviewedRecordsInMemory,
  nowMs: Date.now(), apply: false, rebindExactListing: reviewedTransactionBoundListingResolver });
```

## Existing harvester and KB CLI limitations

The catalog proxy defaults its upstream to `http://localhost:8008`. A deployed catalog service without `INGREDIENT_HARVESTER_BASE_URL` and a reachable FastAPI worker will return 502. A stable worker requires durable `HARVESTER_DB_URL`, ready parser, and either `HARVESTER_QUEUE_MODE=inline` or Redis plus an RQ worker. Starting the service initializes its own schema, so deployment is a distinct reviewed infrastructure action. Search credentials are optional for a supplied PDP; generic fallback search is not permitted for the frozen exact-source lane.

The harvester CSV bridge accepts `candidate_id` and `sku_key`, but drops explicit merchant/platform/variant scope. Set both IDs to the same immutable signature/external ID. Empty task/audit row-ID lists select the whole import, so always pass a validated nonempty exact membership of at most 17. `mode=reviewed` exports all rows with review metadata, not only approved rows. Its `updated_at` changes on import/audit/review and cannot attest a fresh fetch. Keep the actual source capture and listing manifest in memory alongside its result.

The current catalog KB CLI uses `--csv` (the skill's `--csv-path` is stale), and its gate flags default to permissive empty values. Strict historical use requires `--only-parse-status OK --only-review-status APPROVED --only-audit-status PASS --require-ingest-allowed`. It uses candidate ID before SKU key, a globally unique SKU key without market, blind upserts and ingestion timestamps. It also currently loses parsed `inci_list_json` because its helper's JSON conversion body is misplaced. It is unsuitable for this exact reviewed publication lane, especially conflicts, cross-market rows and stale-source repair. This change does not modify that separate repository or claim the legacy CLI is repaired.
